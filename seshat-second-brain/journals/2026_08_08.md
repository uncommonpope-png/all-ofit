## THE ROOT CAUSE (finally — found with real debugging, not guessing)
- **470 point lights** (main city grid + 21 sovereign void realms + warzone) are all VISIBLE when shaders first compile.
- Intel HD 4600 caps at **MAX_FRAGMENT_UNIFORM_VECTORS = 1024**. 470 lights blew past it → **every MeshStandardMaterial shader failed to compile** → main city rendered BLACK/invisible. Terminals showed because they're MeshBasicMaterial (no lighting shaders).
- The LightingManager's light sweep (cap to 8 visible) ALREADY EXISTED — but it ran on a **500ms timer**, AFTER the first render compiled the giant shaders. Race condition.

## THE FIX (313f3f1)
**Synchronous first-frame light cap**: run the existing sweep ONCE, at the top of `animate()`, BEFORE the first render. 8 visible lights → real MeshStandardMaterial compiles small shaders → city renders WITH full lighting + emissive windows. **No material substitution. All emissive game code works.**

## THE GRAVEYARD (what did NOT work — do not repeat)
1. `dc5ce79` (historic) — global MeshStandardMaterial→Basic kill switch → flat grey boxes, broke main city
2. `45ef76b` (yesterday) — assign `THREE.MeshStandardMaterial = fn` → **frozen ES module namespace throws in strict mode → whole module dies → page won't load at all**
3. `6d42988` — Proxy redirect on the namespace (page loads again) → but basic materials have no `.emissive` → `.setHex/.copy/.lerp` crashes across the codebase (office rings, merchant stalls, GSK avatar, vortex pulse)
4. `__genesisStd` with emissive props assigned post-construction → three.js r160 `refreshUniformsCommon` reads `uniforms.emissive.value` when `material.emissive` is truthy → render path crash every frame

## LESSONS (canonical for this repo)
- **`import * as THREE from 'three'` is a FROZEN namespace. Never assign to its properties in strict mode.** Module dies silently-crashy.
- **MeshBasicMaterial has NO emissive.** Three r160's `refreshUniformsCommon` crashes if `material.emissive` is set on a basic material (no emissive uniform in that shader).
- **The weak-GPU problem is a LIGHT-COUNT problem, not a MATERIAL problem.** Cap visible lights BEFORE first compile; never substitute materials globally.
- **The first-frame light cap is now the load-bearing fix.** If anyone ever removes the LightingManager cap or the first-frame hook, the city goes black again on weak GPUs.
- Guarded `.emissive` call sites (office rings 10499, merchant stalls 14104, ground boost 14938, vortex pulse) — the `if (mat && mat.emissive)` pattern is the house style now.

### KEY INSIGHTS FROM REAL RTS CODE
- **ONE input owner** — OpenRA swaps OrderGenerator per mode. Ours: 5 handlers fighting.
- **Unit decides order** — hover enemy=attack cursor, hover resource=harvest cursor, hover ground=move. Cursor IS command UI.
- **One Selection Set** — plain click=clear+select, Shift=toggle, drag-box with 6px deadzone, double-click<320ms=select all same type.
- **Formation hex-rings** — center + concentric hex rings (6,12,18...), greedy nearest assignment, move marker feedback.
- **Per-unit command queue** — Map<id, Order[]>, Shift=enqueue. This IS the shift-queue mechanic.
- **Pooled visuals** — hover ring (dashed, depthTest:false, renderOrder:89) + selection ring pooled.
- **Facade pattern** — every domain has ONE facade (ordenes.mover, ordenes.atacar, produccion.encolar). UI and AI BOTH call these. Degrades gracefully if system missing.
- **Fixed-tick sim** — 20Hz simulation, orders queued, render interpolated.
